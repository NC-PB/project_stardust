## Description
Use a library for the index (generic area), for example tantivy.

Implements `S-search-fulltext` in the [spec](../spec.md).

## Acceptance criteria
- [x] Searches all files under the planning root, results while typing
- [x] The index is updated incrementally from watcher events
- [x] Thousands of files without noticeable lag (measured on a generated test set of 5,000 files)

## Implementation notes
- Decided with the user (2026-10-31): no search library; Rust scans the lowercased text of all planning files in memory, every query word as a substring (D-20261031-002734-fwvh).
- Done: `domain/search.rs` (`SearchIndex::build`, `apply`, `search`, snippets), `SearchState` shared between the `search` command and the watcher callback of `watch_project`, which updates the index before emitting the batch; `unwatch_project` drops it. Frontend `lib/search.ts` (`highlight`), `stores/search-store.ts` (debounce, stale answers dropped, refresh after batches), `components/search-box.tsx` above the board.
- Timing test `search_5000_files` (ignored by default; `cargo test --release --lib -- --ignored --nocapture search_5000`): release build 113 ms, slowest query 11 ms, update 81 µs; debug 197 ms, 77 ms, 198 µs.
- Checks: `cargo test` (116, one ignored), `cargo clippy` clean, `npm run check` (94). Not tried by hand in the running app.

## Result
A search box above the board finds every planning file that contains all words of the query, in any case, while you type. Ids and node slugs match exactly as typed. Each result shows title, path, line and the matching line with the words marked, and opens in the editor. The text lives in memory, is read when the project opens and follows every watcher batch; nothing is stored on disk. On 5,000 generated files a query takes 11 ms in a release build.
